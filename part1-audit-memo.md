Slice chosen: Skills, Plugins, and Connectors (the take-home's suggested cross-cutting primitives — see `claude/plan.md` for why).

Status: draft, built live with Megan. Sections below fill in as we finish them. Red-teamed against live pages on 2026-09-17 — see the log at the very end of this doc for what those passes found and fixed, including a correction to finding #3 caught during Part 3's build.

## What's actually wrong (prioritized)

### P0 — fix now: concrete, cheap, and either actively wrong or actively risky

**1. Plugin installs carry no warning at the point of installation, despite plugins being riskier than connectors.**
A connector exposes callable tools; a plugin can bundle local MCP servers, skills with executable Python/JS/Bash scripts (which Claude will run, installing PyPI/npm dependencies those scripts declare), and hooks that fire automatically at session lifecycle points rather than on a discrete user-triggered call. That's a materially larger attack surface, and the riskiest install path — adding an arbitrary Git repo as a plugin "marketplace" — is documented in `cowork/guide/plugins.md` as a plain feature with zero caution language.

`plugins/submit.md` does acknowledge the risk ("Plugins are capable of loading remote MCP servers, local MCP servers, and other local software tools... review any additional software that may be installed") — but that page is written for people *submitting* a plugin, not installing one. The actual install flow (`cowork/guide/plugins.md`: Browse → Install → Review components) carries no risk language and doesn't link to the one page that has it. Compare to connectors, which get a full trust-model page (`connectors/verification.md`) written for and linked to the installer.

The estate already has a working pattern for exactly this, too, just not applied here: `office-agents/connectors-and-skills.md` puts a `<Warning>` — with a link to further guidance — directly in front of the instruction to enable a custom connector in Claude for M365. So the fix isn't "invent pre-install risk disclosure" — it's "apply the pattern that already exists elsewhere in the estate to the one primitive currently missing it."

This is my own severity argument, worth naming as such rather than as settled fact: I haven't found anywhere in the estate that Anthropic states this risk ordering (plugins > connectors) explicitly as an official position — I built the case from what each primitive can technically do. A reasonable reviewer could push back that a connector with write access to a production system carries comparable risk to a sandboxed local script. I think the asymmetry holds — automatic, non-discrete triggers (hooks) plus local execution is a broader surface than a callable tool — but flagging that this is argued, not cited.

Fix is cheap — one installer-facing page plus two links — and the timing matters: plugin sharing is currently local-only/beta, so this is fixable before the install surface scales to org-wide sharing.

**2. A cross-reference — repeated three times on one page — sends Cowork admins to the wrong deployment model's docs.**
`cowork/guide/plugins.md` links to `/docs/cowork/3p/extensions` three separate times: once right after the Git-repository-marketplace instructions, once under "Plugins managed by your organization," and once in the page's own "Related" list — all three with the same anchor text, "MCP, plugins, skills, and hooks." The page that actually exists at that title, `/docs/third-party/claude-desktop/extensions.md`, is scoped to Claude Desktop deployed through third-party LLM platforms (Bedrock, Vertex, gateways) — not to Cowork's own org/admin plugin management. An admin following any of the three either hits a mismatch or starts applying a different deployment model's configuration guidance to their Cowork org. Three identical, independently-wrong instances of the same link on a single page is stronger evidence than one — though worth being precise about what it's evidence *of*: it shows nothing currently catches a wrong link once it exists, not necessarily that the link was wrong from the moment it was written. (It's equally plausible the link was correct when authored and broke later when the target page moved or was restructured — I have no page-history access to distinguish "never checked" from "checked once, then rotted." Either way, the fix and the underlying process gap are the same.)

*Correction, 2026-09-19:* Part 3's link checker initially misclassified all three instances of this link as `BROKEN` ("target path not found"), and its run log went further, calling it a link to a path that was "renamed or never existed as written" — an inference never actually confirmed by a live fetch. It was wrong: `https://claude.com/docs/cowork/3p/extensions` resolves to full, real content, titled "MCP, plugins, skills, and hooks" — the exact page this finding already describes. The page is real, just missing from both `sitemap.xml` and `llms.txt`, the same under-indexing pattern as finding #3's four pages below, not a dead link. This finding's actual point is unchanged — the link sends Cowork admins to the wrong deployment model's docs — but it's a wrong-destination problem, not a broken-link problem, and the checker's initial classification conflated the two. See `part3/data/verified_overrides.json` and `part3/output/run_log.md` for the corrected checker output.

### P1 — root cause and its symptoms: higher-leverage, harder to fully resolve in one pass

**3. `llms.txt` and `sitemap.xml` — the site's two machine-generated indexes — disagree with each other on a handful of pages, and the first version of this finding got the disagreement backwards.**
An earlier pass of this audit claimed `connectors/building/mcpb.md` was a live page missing from `llms.txt`. That claim doesn't hold up under a clean re-check: a complete, literal fetch of `llms.txt` done for Part 3's data prep shows the page listed there in full ("Build a desktop extension with MCPB"), and I have no record of ever having actually confirmed the original claim with a literal read of the file rather than a summarized one — an earlier attempt at a literal fetch failed outright and got worked around at the time by trusting an older, non-literal read instead, which is the likely source of the error. Retracting that claim rather than defending it.

What's actually verified — independently, by direct fetch and by Megan opening each page herself — is the opposite asymmetry: `sitemap.xml` is missing four real, live pages that `llms.txt` correctly lists: `claude-tag/admins/healthcare`, `third-party/claude-desktop/connectors-box`, `connectors-google-cloud`, and `mcp-sign-in`. So on current evidence `llms.txt` is the more complete of the two indexes here, not the less complete one — the reverse of the original framing. (One more page, `third-party/claude-desktop/models`, briefly looked like a second example of the same pattern — `llms.txt` lists it, `sitemap.xml` doesn't — until a live check said otherwise: my own tool returned a false 404 for it twice in a row, most likely a stale cached error, while the `.md`-suffixed variant and Megan's own browser both loaded it fine. Also retracted; also a reminder that a link checker's own fetches need to be trustworthy before its verdicts are — see the red-team log below and the Part 3 checker's own notes on this.)

Demoting this out of P0: four pages out of 237 is real but narrow — three of the four sit under `third-party/claude-desktop`, a section that isn't central to this slice, and there's no evidence either index is unreliable specifically for Skills/Plugins/Connectors (the two sources agree exactly on the Connectors count — both list 37 — see finding #7). This is still worth fixing and still supports Rule 3's premise that link/index checks need more than one source of truth, but it doesn't carry the same active-harm urgency as #1 and #2.

**4. Skills and Plugins have no canonical, site-owned definition.**
Both primitives' deepest authoring/technical reference lives on code.claude.com/docs (out of scope for this audit, but worth naming as the reason claude.com/docs's own pages read thin) — `skills/overview.md` and `plugins/overview.md` each point outward for "the real docs" rather than owning a complete definition. Every surface page that needs to explain "what is a plugin" is left to reconstruct that definition from scratch, with nothing to defer to. This is the finding that explains #5 and #6 below, and one I'd prioritize highly among the structural items, because fixing it prevents the other two from recurring as new surfaces ship.

**5. "What a plugin contains" is answered differently on four different pages.**
`plugins/overview.md` and `plugins/submit.md` both say skills + MCP connectors + slash commands + sub-agents (no hooks). `cowork/guide/plugins.md` says skills + connectors + agents + hooks. `government/desktop/plugins.md` says skills + slash commands + sub-agents + hooks, dropping connectors from the primary sentence. None of these is exactly wrong — they're uncoordinated restatements of the same list, invisible to any one page's author and only visible when you read the estate end to end. This is also the natural candidate for the Part 3 automated checker: mechanically detectable by diffing enumerated component lists across pages that define the same term. *(Confirmed by Part 3, 2026-09-17: the Rule 1 checker built for this exact purpose found the pattern runs deeper than the tables cited above — `government/desktop/plugins.md`'s opening* definitional sentence *— not a table, the actual "a plugin is..." claim — independently asserts hooks as a plugin component, and a second, more detailed instance later on the same page claims hooks specifically "run on your machine at defined points during a session," a mechanism claim canonical `plugins/overview.md` makes nowhere at all. See `output/semantic_drift_findings.md` in the Part 3 repo.)*

*Direction corrected, 2026-09-19:* Pass 4 below treated the "hooks" gap as canonical `plugins/overview.md` being right and the surface pages being wrong. That direction doesn't hold up: `cowork/guide/plugins.md`'s own live "What a plugin can contain" table — the same table Part 2's before/after rewrite works from — lists Hooks as a real component too, right alongside Skills, Connectors, and Agents. That's two independent, live surface pages (Cowork and Government) agreeing hooks are real, against one canonical page that doesn't mention them. The more likely read is that `plugins/overview.md` is the stale one here, not that Government invented a capability — the fix this finding actually points to is "add hooks to canonical," not "remove hooks from Government." The underlying problem (four pages, four uncoordinated lists, no single source of truth) is unchanged either way; only the direction of the individual fix is. See `part3/output/semantic_drift_findings.md`, "what changed in the fifth pass," for the full cross-check.

**6. Definitions get re-derived instead of linked, which is how drift starts.**
`government/desktop/skills.md` restates SKILL.md's frontmatter and folder-structure rules — already fully specified in `skills/how-to.md`, which it does link to — instead of treating that page as the single source of truth and adding only what's genuinely Government-specific (the text-only file rule, the plugin-wrapper packaging requirement). Low risk today since the two descriptions still agree, but it's the exact pattern that goes stale first: if a frontmatter field limit or required key changes, there's no single place to update and nothing that would catch the two pages drifting apart. *(Confirmed by Part 3, 2026-09-17: the Rule 1 checker independently re-derived this exact problem from live data — the "Building and deploying your own skills" section on this page runs 25 sentences and walks through frontmatter format, folder-naming rules, plugin packaging, manifest keys, upload, and testing, a clean instance of Part 2's Rule 5(b) — "no restating authoring/build content on a Tier 3 page" — not just a borderline restatement. See `output/semantic_drift_findings.md`, candidate #5, in the Part 3 repo.)*

## What should be deleted or merged

General principle applied below: a **merge** collapses duplicated content into one page and trims the others down to a link (no URL disappears, so no redirect is needed) — a **deletion** retires a URL entirely and needs a redirect target plus an update to every page that still links to it (including `llms.txt` itself, since it's a first-class navigational artifact this role explicitly owns and the assignment itself points people to).

**Merge — trim the re-derived "what is a plugin / what is a skill" preambles down to a link, once a canonical definition exists (depends on finding #4 above).**
`government/desktop/skills.md`, `government/desktop/plugins.md`, and `cowork/guide/plugins.md` each open with their own restatement of what a skill or plugin is before getting to genuinely surface-specific content (Government's text-only/packaging rules, Cowork's install steps). None of these pages should disappear — the procedural content is real and correctly scoped to its surface. What should go is the redundant preamble: replace it with one or two sentences plus a link to the canonical definition. This directly fixes finding #5 (four different component lists) by removing three of the four places that list currently gets restated. No redirect needed — same URLs, less duplicated content.

**Merge — fold `plugins/submit.md`'s "What makes a good plugin" section into `plugins/overview.md`.**
`submit.md`'s "What makes a good plugin" section (bundle skills + connectors + slash commands + sub-agents into one coherent package, with the sales-plugin example) substantially overlaps `overview.md`'s "How plugins compose capabilities" table — same concept, same example pattern, explained twice on two different pages with two different framings. `submit.md` should stay focused on submission mechanics (directory vs. your own marketplace vs. direct install, review process, terms) and point back to `overview.md` for what a good plugin looks like conceptually. Same reasoning as above: a trim, not a deletion, no redirect needed.

**Restructure and partially delete — `connectors/getting-started.md`.**
This page mixes two things that should be separated. The "Connector-specific tips" section (Google Drive is best for X, Slack requires the earlier Claude in Slack app first, and so on) is genuinely durable, judgment-level content that belongs merged into `connectors/overview.md`'s "Types of connectors" section, next to the concepts it's actually tips *about*. The step-by-step UI click-path ("Select Customize in the sidebar... Click Connect next to your chosen service...") and the troubleshooting accordion are the kind of content that goes stale the moment the UI changes, and the estate already has a working pattern for this: `office-agents/connectors-and-skills.md` deliberately does *not* document click paths locally and instead links out to a support.claude.com article for exactly this reason (and, per finding #1's added evidence above, that same page is also where the estate's one working example of pre-install risk disclosure lives). `connectors/getting-started.md` should follow the same pattern — once the tips are merged out, there's nothing left on this page that a support-center article (or a short "see Customize > Connectors in-app" pointer) doesn't already cover better and keep current on a faster-moving process. That makes this page a genuine deletion, not just a trim.

Because it's a deletion, the URL needs a real answer for readers who land on it afterward:
- **Redirect `connectors/getting-started.md` to `connectors/overview.md`.** It's the nearest living parent and, post-merge, contains the durable content that used to live on the deleted page — so a reader who lands there via an old bookmark or search result isn't dropped somewhere unrelated, they get the improved version of what they were looking for.
- **Update the one on-site backlink first.** `connectors/overview.md`'s own "Next steps" card currently points to this page — that has to change in the same edit, or the redirect just bounces the reader back to where they started.
- **Update `llms.txt`** to drop the merged entry, so a Claude session (or any other tool) using the index as a map doesn't keep citing a URL that no longer resolves to standalone content. (Given finding #3, this is also a good forcing function to audit `llms.txt` — and `sitemap.xml` — against the live site and each other more broadly, not just for this one page.)

**Flagged but not yet fully substantiated — scope for a follow-up pass.**
The pattern above (surface pages re-deriving primitive definitions instead of linking) showed up consistently everywhere I checked it: Government, Cowork, and — going by page titles and framing alone, not yet read in full — likely also `government/connectors/overview.md` and `claude-science/connectors-and-skills.md`. I'd bet on the same finding there, but I haven't read those pages closely enough to put them in a "delete or merge" recommendation with the same confidence as the ones above, so I'm flagging them as the first place I'd extend this audit rather than asserting a specific fix. Similarly, the ~37-page Connectors section (MCP Tunnels, Building Custom Connectors, MCP Apps) almost certainly has its own internal duplication given how consistently the pattern showed up elsewhere, but a full pass through those subsections was out of scope for the time I had here.

## Proposed information architecture

The current shape is a flat list per primitive (Skills has 2 pages, Plugins has 2, Connectors has 37 in one bucket) plus an unbounded number of surface sections that each independently decide how much of the primitive to re-explain. That flatness is *why* findings #4–#7 exist: there's no structural slot for "the one true definition" versus "how this works in Cowork," so every page ends up deciding that boundary for itself, inconsistently.

I'd reorganize each primitive (Skills, Plugins, Connectors) around the same three-tier pattern, so the pattern itself — not tribal knowledge — is what tells a new contributor where content goes:

**Tier 1 — Concepts.** One canonical page per primitive: what it is, how it relates to the *other two* primitives (this cross-referencing currently happens by hand, differently, on `skills/overview.md`, `plugins/overview.md`, and `connectors/overview.md` — it should be generated from one shared definition, not restated three times), and a single availability-by-surface table. This tier is normative: every other page that needs to say "what is a plugin" links here instead of re-deriving it. `skills/overview.md`, `plugins/overview.md`, and `connectors/overview.md` are already roughly the right shape for this tier — the work is mostly enrichment and enforcement, not relocation, which keeps this phase low-risk (no URL changes).

**Tier 2 — Build / Author.** How to create the thing: `skills/how-to.md`, the Connectors `building/` tree (MCP server, remote vs. local vs. MCPB, MCP Apps, submission), and a genuine plugin-authoring guide (which barely exists today — `plugins/submit.md` conflates "how to build a good plugin" with "how to submit one," per the merge recommendation above). Standardizing this tier under a consistent path pattern per primitive (e.g., `/<primitive>/build/` for all three) is what actually resolves the 4-vs-37 imbalance at the structural level — not by forcing Skills to artificially grow to 37 pages, but by making it legible that Skills' authoring guide is short *because skills are simple*, not because nobody got around to writing more. MCP Tunnels and MCP Apps, in particular, read less like siblings of "Connectors" and more like deployment/rendering sub-features that belong nested under Connectors' Build tier rather than at the same top-level as Connectors itself.

**Tier 3 — Use in [surface].** Cowork, Government, Desktop-3P, M365, Claude Science, Claude Tag each keep their own page(s) — this tier is not going away, and shouldn't; installation UI and admin controls genuinely differ by surface. What changes is what these pages are *allowed* to contain: only what's actually different at that surface (install steps, admin controls, availability, surface-specific limits like Government's text-only skill rule), governed by the template from Part 2 and enforced by the Part 3 checker rather than hand-review. This is where findings #5 and #6 get structurally prevented going forward, not just patched once.

*Caveat added after stress-testing the Part 2 template against real Tier 3 candidates (see `part2-standards.md`'s dated note): this per-primitive page shape fits Cowork, Government, M365, and Desktop-3P cleanly. It does not fit Claude Tag, whose admin content is organized by task and scope rather than by primitive — a genuine structural difference, not a compliance gap. The IA and the template both need to treat "single-primitive Tier 3 page" as the common case, not a universal requirement, and give a surface like Claude Tag its own pattern rather than forcing this one.*

One cross-cutting piece worth calling out explicitly: **trust/verification should be a single shared concept, presented consistently for all three primitives**, not connectors-only. Right now `connectors/verification.md` is a full page and plugins get a paragraph; in the proposed IA, verification is part of Tier 1 for each primitive, written from a shared template so the risk guidance is proportional to risk (per finding #1), not to which team happened to write more.

**What it would take to get there — sequenced by risk, not by importance:**

1. *No URL changes (do first, this week's scope).* The merges already listed above — trim the restated definitions, fold `submit.md`'s overlap into `overview.md`. This is most of the value in Part 1 with none of the redirect risk.
2. *Enrich Tier 1, still no URL changes.* Turn the three `overview.md` pages into the actually-canonical source — including the missing plugin-installer trust page from finding #1 — so Tier 3 pages have something real to link to instead of re-deriving.
3. *Reorganize Tier 2 under a consistent pattern.* This is the one phase that likely does move URLs (especially inside the Connectors `building/` tree), so it's sequenced last and should follow the redirect discipline established in the delete/merge section above — at scale, not ad hoc, and with an audit of both `llms.txt` and `sitemap.xml` against each other and the live site as part of the same change, given finding #3.
4. *Roll out the Tier 3 template — to the surfaces it actually fits.* Six-plus surface sections, none of which report to this role — this is a standards-and-adoption problem, not a one-time cleanup, which is exactly what Part 2 (the template) and Part 4 (adoption without authority) are for. I wouldn't try to hand-fix all six surface sections myself; I'd ship the template and the checker and let teams apply it to their own pages, the same way any other cross-cutting standard has to spread in an org where nothing reports up to one owner — and I'd say plainly, up front, that Claude Tag needs its own pattern rather than pretending the template covers it too.

## What to measure / instrument

Grouped by how directly each metric ties back to the findings above, and how honest I can be about whether the instrumentation already exists.

**Leading indicators — cheap, automatable, and directly the job of the Part 3 checker**

- *Internal link validity*: % of internal links across the slice that resolve to a page confirmed live. Target: 0 broken/orphaned links, checked pre-merge, not just discovered by someone stumbling into them (which is how #1 and #2's supporting details, and #3, were found or corrected during this audit). This is the most literal, falsifiable metric in this memo, and it's exactly what Part 3 builds.
- *Definition-consistency count*: number of distinct, conflicting restatements of a term that should have one definition (the "what's in a plugin" problem from #5). Target: trending from 4 toward 1 canonical source + N pages that link to it, 0 pages that restate it independently. Same checker, different rule.
- *Tier-1/Tier-3 boundary compliance*: once the IA above exists, the number of Tier 3 (surface) pages that contain a from-scratch primitive definition instead of a link to Tier 1. This is the metric that tells us whether #6's pattern (re-deriving instead of linking) is actually going away, not just fixed once in the two pages I found it in.
- *Security-coverage parity*: a simple checklist, not a continuous metric given there are only three primitives — does each of Skills/Plugins/Connectors have a linked, installer-facing trust/verification page? Binary today (connectors: yes, plugins/skills: no); target is yes for all three.

**Lagging indicators — do the fixes actually change reader outcomes**

Confirmed: claude.com/docs already has an on-page reader feedback widget with a thumbs up/down and a categorized follow-up on both paths. On "Yes" ("What worked best for you?"): *the guide worked as expected* / *it was easy to find the information I needed* / *it was easy to understand the product and features* / *the documentation is up to date* / *something else*. On "No" ("How can we improve our product?"): *help me get started faster* / *make it easier to find what I'm looking for* / *make it easy to understand the product and features* / *update this documentation* / *something else* — each with an optional free-text field. The two sides are matched pairs, which means this is a genuine before/after instrument, not just a satisfaction score:

- *Findability* — "easy to find what I needed" (Yes) / "make it easier to find what I'm looking for" (No) — the direct signal for whether the Tier 1/2/3 reorg above is working, tracked on the pages it touches.
- *Freshness* — "documentation is up to date" (Yes) / "update this documentation" (No) — direct staleness signal, relevant to #3 (index/live-site drift) and #6 (definitions drifting apart).
- *Clarity* — "easy to understand the product and features" (Yes) / same wording (No) — the definition-consistency signal, ties directly to #5's four conflicting "what's in a plugin" lists.
- *Onboarding/correctness* — "guide worked as expected" (Yes) / "help me get started faster" (No) — not a perfect mirror, but the closest match to #2's wrong cross-reference: an admin following that link is having their task actively fail, which is exactly what this pair is built to catch.
- *"Something else" + free text (both sides)* — where a reader would describe something that doesn't fit a category, like the specific shape of #2. A light manual tagging pass on this free text, mapped against this memo's finding taxonomy, turns it into an early-warning signal rather than just a count.

Because "No" already breaks down by these categories, category-level "No" rate on the specific pages this audit changes, before vs. after each fix ships, **would be** a clean, already-instrumented metric with zero new tooling required — *if* the underlying responses are actually queryable per page and per category, not just displayed to the reader at submission time. I can confirm the categories exist and that a reader sees them (from screenshots of the live widget); I can't confirm from outside the org whether whoever owns this tool can actually pull "No, category: findability" filtered to a specific URL, over a specific date range. I considered this the single best lagging indicator available for this audit, and I still think it probably is — but I'm flagging the querying question as **considered, not confirmed**, rather than asserting it as a ready-made metric. It's the first thing I'd verify with whoever owns the feedback tool's backend before treating "wire up before/after views per finding category" as a checkbox item; if only site-wide aggregate counts are exposed today, standing up a page-level view might itself be the first concrete ask this audit produces for Part 4.

Beyond the feedback widget, the other lagging signals I'd want (and haven't confirmed exist, so flagging rather than asserting):
- Support-ticket volume and tags referencing Skills/Plugins/Connectors confusion, before/after the fixes ship.
- Funnel completion for "install your first connector" and "install your first plugin," if product analytics tracks page view → connect/install click → successful completion. `connectors/getting-started.md` documents exactly this funnel today, which hints the instrumentation may exist for connectors and would just need extending to plugins.
- Page-level engagement (time-on-page, bounce/exit rate) on the specific pages this audit touches, before/after.

The feedback widget confirms at least one of these categories of instrumentation is already in place — worth checking whether the other three are too before proposing anything that would duplicate existing tooling.

**Adoption indicators — tie to Part 4**

- Number/share of Tier 3 surface pages that pass the checker as template-compliant, tracked over time per owning team. This is the number that actually answers "is the standard working," since the standard's whole point is to be followed by teams that don't report to this role.
- Time from a Tier 1 canonical definition changing to its dependent Tier 3 pages being reviewed (not necessarily changed — reviewed). A short lag here means the drift pattern in #6 is structurally prevented; a long or infinite lag means the standard exists on paper but isn't actually load-bearing.

**How I'd instrument it**: the Part 3 checker is doing double duty as both the enforcement mechanism and the leading-indicator dashboard — it should run on a schedule against the live site, not just gate PRs, and its output should go somewhere a human actually looks (a dashboard or a recurring digest), not just a CI log that only gets read when something fails. For the lagging indicators, the feedback widget's category breakdown is the cheapest win *if* it's queryable the way I'm hoping — it likely just needs a saved segment/filter per finding category rather than new instrumentation, but that's contingent on the open question flagged above. The adoption indicators need a home too, most likely a short recurring review (monthly, given the pace docs changes at) rather than a one-time report, since the whole thesis of this audit is that these problems recur if nothing keeps checking.
